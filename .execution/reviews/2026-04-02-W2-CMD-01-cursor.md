## Aligned

### BP-07 §Command Interaction Rules: No hidden daemon start or write side effects

All five read-only entry points (`show`, `list`, `search`, `export`, API
routes) follow the same pattern:

1. `getStore(configDir())` — opens SQLite directly (singleton, runs
   idempotent migrations per BP-05)
2. Execute read-only SQL queries
3. Format and return output

No command imports or calls `startDaemon`, `watchCommand`, `startCommand`,
`markRuntime*`, `acquireOwnership`, or any pipeline/watcher code. No
command writes to `_jin_sync`, `_jin_push_state`, or `conversations`.
The `export` command writes files to an output directory (user-specified
or `./jin-export`), not to the store.

(`src/commands/show.ts`:12, `src/commands/list.ts`:11,
`src/commands/search.ts`:16, `src/commands/export.ts`:15,
`src/api/routes.ts`:30)

BP-07 §Read-only commands: "may open SQLite directly, return useful output
even when jin is stopped. Must not start a hidden second runtime. Must not
mutate conversation state as a side effect." **Fully satisfied.**

### BP-07 §Query commands do not require the daemon

The test `list/search/show work while stopped and do not create runtime state`

- No `jin.runtime.json` or `jin.pid` files created

### BP-03 §Views Over the Model: Single conversation, full trace, tree

The `show` command implements all three BP-03 views:

**Single conversation** (`show.ts`:48-58):
- `store.getMessages(conversation.id)` — matches BP-03 §Single Conversation:
  `WHERE conversation_id = ? ORDER BY sequence`

**Full trace** (`show.ts`:61-90):
- `getTraceConversations(db, traceId)` uses
  `WHERE trace_id = ? ORDER BY started_at` — matches BP-03 §Full Trace data
  fetch pattern
- `buildConversationTree(conversations)` reconstructs the tree from
  `parent_id` — matches BP-03 §Full Trace rendering algorithm
- `renderTraceNode` walks the compaction chain (compacted children rendered
  at same depth with `--- compacted continuation ---` separator) and
  interleaves spawned children at their `fork_point` turn — matches BP-03
  §Full Trace steps 3-6

**Tree view** (`show.ts`:92-116):
- Uses same `getTraceConversations` + `buildConversationTree` —
  matches BP-03 §Conversation Tree pattern
- `printTreeRoot/printTreeNode` renders indented hierarchy with
  relationship labels and fork_point annotations

(`test/read-only-query-surface.test.ts`:61-94 verifies trace and tree
views with 3 linked conversations: root, spawned child, compacted
continuation)

### BP-03 §Trace Properties: Tree construction

`buildConversationTree` in `query-surface.ts`:158-186:
- Groups conversations by `parentId` into a children map
- Sorts children by `startedAt` (deterministic ordering)
- `pickRootConversation` finds the root via 5-level fallback:
  `relationship === "root"` → `parentId === ""` → `id === traceId` →
  orphan check → earliest by date
- Cycle protection via `visited` set in recursive tree builder

This correctly handles the BP-03 invariants:
- Every trace has exactly one root (invariant 9)
- parent_id references within same trace (invariant 4)
- Compacted segments form a chain (invariant 6)

## Drift

### D1. `routes.ts` ignores the passed `store` parameter — informational

`createRoutes(store: unknown)` at `routes.ts`:27-30 receives a `store`
parameter but immediately calls `getStore(configDir())` instead. This
decouples the API routes from whatever store the caller provides. The
`void store` on line 29 confirms this is intentional. This is fine for
the read-only surface (same singleton either way), but when the API
server is invoked from the daemon with an already-open store, this creates
a second entry path. **Not blocking** — cosmetic, and the singleton cache
in `getStore` returns the same instance anyway.

File: `src/api/routes.ts`:27-30
BP ref: BP-05 §Singleton

### D2. `export` command creates directories and writes files — informational

`exportCommand` at `export.ts`:20-21 creates an output directory and writes
files via `Bun.write`. This is the expected behavior of an export command
(it exports data to disk), but it is technically a write-to-filesystem
operation. The packet acceptance checks focus on "no hidden daemon start or
write side effects" in the context of store mutations, not file export.
**Not blocking** — this is the command's purpose, not a side effect.

File: `src/commands/export.ts`:18-21
BP ref: BP-07 §Read-only commands

### D3. `routes.ts` legacy API shape bridge is wide — informational

`toSessionLike` at `routes.ts`:198-251 produces a 40+ field object with both
camelCase and snake_case variants, plus v1 compatibility fields
(`isSubAgent`, `parentSessionId`, `isCompacted`, `adapterName`,
`adapter_name`, `total_tokens`). This is a deliberate backward-compatibility
bridge for existing API consumers (likely the Desktop/TUI surface). It does
not violate any BP or frozen contract — it adds fields, doesn't change
semantics. **Not blocking** — but Codex should track this for eventual cleanup
when v1 API consumers are retired.

File: `src/api/routes.ts`:198-251
