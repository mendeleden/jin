## Aligned

### BP-02: Serial Coordinator

The coordinator in `loop.ts:177-269` is a single `while(true)` loop that
calls `queue.take()` and processes one work item at a time. No concurrent
ingest or push calls. Watcher callbacks, periodic timers, and shutdown all
enqueue work — none call `ingestAll()` or `pushDirty()` directly. This
matches BP-02 §"The coordinator is the single arbiter" exactly.

- `loop.ts:177` — `async function coordinator()`
- `loop.ts:179` — `const work = await queue.take()` blocks until work available
- BP-02 §Serialization: "no concurrent calls to the same adapter instance" ✓

### BP-02: Work Queue and Coalescing

`WorkQueue` in `queue.ts` implements the coalescing contract from BP-02
§Push Scheduling:

- Adjacent `{ kind: "push" }` items coalesce (`queue.ts:65-66`) ✓
- Adjacent `{ kind: "reconcile-adapters" }` items coalesce (`queue.ts:69-73`) ✓
- Same-adapter `ingest-adapter` fs-change items merge `changedPaths`
  (`queue.ts:76-91`) ✓
- `take()` blocks on an empty queue via promise-based waiter pattern
  (`queue.ts:22-31`) ✓

### BP-02: Ingest Phase

### BP-02: Change-Gated Push Scheduling

Push is only enqueued when ingest reports `anyChanged`:

- `loop.ts:204-206` — after `ingest-all`, `if (result.anyChanged) enqueuePush()`
- `loop.ts:229-231` — after `ingest-adapter`, `if (result.anyChanged) enqueuePush()`
- `enqueuePush()` returns early if `stopping` (`loop.ts:272-278`) ✓
- Queue coalescing prevents push storms: adjacent push items merge in
  `tryCoalesce()` ✓

This is the exact BP-02 §Push Scheduling contract: "When `writeBundle()`
reports `changed: true`, the coordinator enqueues a `{ kind: "push" }` work
item."

### BP-02 / BP-07: Shutdown Semantics

`loop.ts:124-175` implements shutdown:

1. `stopping = true` — coordinator skips normal work (`loop.ts:184`) ✓
2. `watcher.close()` — stops file watching (`loop.ts:135`) ✓
3. `clearInterval(periodicTimer)` — cancels periodic timer (`loop.ts:137-139`) ✓
4. `queue.discard()` — discards all pending normal work (`loop.ts:141-143`) ✓
5. `queue.enqueue({ kind: "shutdown-flush" })` — one final flush (`loop.ts:144`) ✓
6. `Promise.race` with `shutdownDrainTimeoutMs` (defaults to
   `SHUTDOWN_DRAIN_TIMEOUT_MS` = 15s from frozen lifecycle contract) ✓
7. On timeout: log + call `onShutdownTimeout` callback ✓
8. On clean exit: `sink.close()` for all sinks via `Promise.allSettled` ✓
9. Sink close errors caught individually (`loop.ts:166-170`) ✓

The shutdown-flush work item runs one final `ingestAll()` + `pushDirty()`
(`loop.ts:241-256`), matching BP-02 §"one shutdown ingest scan + one final
push."

**Key correctness detail:** The `queue.discard()` call at line 141 discards
all items *except* `shutdown-flush`, then immediately enqueues the shutdown
flush. Since the coordinator may still be processing an in-flight work item
(the `currentWork` it already took from the queue), the flush won't run
until that in-flight item finishes. This matches BP-07 §"wait for any
in-flight work item to complete."

## Drift

### I1 — `SHUTDOWN_SCAN_HINT` uses `periodic-scan` instead of dedicated `shutdown-scan` kind (informational)

- **File:** `loop.ts:31`
- **Finding:** BP-02 pseudocode uses `{ kind: "shutdown-scan" }` for the
  final flush hint. The frozen `ADAPTER_CHANGE_HINT_KINDS` in
  `contracts/adapters.ts` only includes `startup-scan`, `fs-change`, and
  `periodic-scan`. The worker correctly chose to reuse `periodic-scan`
  rather than widening the frozen contract. A code comment explains this
  decision.
- **Severity:** Informational. Semantically correct — both hint kinds trigger
  a full scan. The adapter contract does not need a fourth hint kind for
  this. No action needed.

### I2 — `PipelineHandle.enqueue()` exposed on the public handle (informational)

- **File:** `types.ts:80`, `loop.ts:98-99`
- **Finding:** The `PipelineHandle` interface exposes `enqueue()`, allowing
  external callers to inject work items into the coordinator's queue. BP-02
  only mentions watcher and periodic timer as intake channels. The worker
  uses this for testability (tests call `handle.enqueue()` directly to
  simulate watcher events). This is not a BP violation — it's a superset
  that doesn't contradict the blueprint — but it means the pipeline handle
  has a wider API surface than BP-02 strictly requires.
- **Severity:** Informational. The `enqueue()` method is useful for both
  testing and future one-shot `jin ingest` support. No action needed.

### I3 — Deferred BP-02 features: per-adapter timeouts, error tracking, RSS monitoring (informational)

- **File:** BP-02 §Per-Adapter Timeout, §Resource Budget
- **Finding:** BP-02 specifies per-adapter timeouts (30s per
  `loadConversation`, 60s per `findChanged`), consecutive error tracking
  (3 failures → adapter disabled), and RSS monitoring (256 MB hard limit).
  The frozen contract defines `DEFAULT_FIND_CHANGED_TIMEOUT_MS` and
  `DEFAULT_LOAD_CONVERSATION_TIMEOUT_MS`. The worker's implementation does
  not include these features — adapter calls have no timeout wrapper, no
  error count tracker, and no RSS checks.
- **Severity:** Informational. The packet's acceptance checks do not require
  these features, and the frozen timeout constants exist for future use.
  These are follow-ups for a hardening packet, not blockers for the spine.
  The serial coordinator's error handling (log + skip) is sufficient for
  the initial end-to-end path.

### I4 — Startup work enqueued after `runPipeline()` returns the handle (informational)

- **File:** `loop.ts:88-96`
- **Finding:** The coordinator loop starts immediately (`loop.ts:88`), but
  startup work is enqueued at lines 90-96, *after* the coordinator promise
  is stored. Since the coordinator blocks on `queue.take()`, it won't
  process anything until work is enqueued. However, if the coordinator were
  somehow faster than the enqueue (e.g., different runtime scheduling),
  the startup work could arrive while the coordinator is idle. In practice,
  `queue.take()` blocks on a waiter promise, and the enqueue resolves that
  waiter, so the ordering is safe. But the BP-02 pseudocode enqueues
  startup work before starting the coordinator.
- **Severity:** Informational. No runtime bug — the promise-based waiter
  pattern in `WorkQueue` guarantees correct ordering. A cosmetic reorder
  (enqueue before coordinator start) would match the BP-02 pseudocode more
  literally but is not functionally necessary.
