## Aligned

### BP-02: Serial Coordinator

The coordinator in `loop.ts:177-269` is a single async while loop. All work
items are drained one at a time via `await queue.take()`. No parallel
adapter calls, no concurrent ingest or push. This is the BP-02 design:
"correct by construction" serialization without locks.

`currentWork` tracks the active item. Only one item is processed at any
time. Watcher callbacks, periodic timers, and shutdown all enqueue work —
none call `ingestAll()` or `pushDirty()` directly. Matches BP-02 §"The
coordinator is the single arbiter."

### BP-02: Queue and Work Items

`queue.ts` implements the work queue from BP-02. Five work item kinds match
the blueprint pseudo-code exactly: `reconcile-adapters`, `ingest-all`,
`ingest-adapter`, `push`, `shutdown-flush`.

Coalescing (`queue.ts:59-94`):
- Adjacent `push` items coalesce (prevents push storms)
- Adjacent `reconcile-adapters` items coalesce
- Adjacent `ingest-adapter` items for the same adapter with `fs-change`
  hints merge their `changedPaths` arrays

`QueueablePipelineWorkItem` excludes `shutdown-flush` from external
enqueue — only shutdown can inject it. Type-safe gate.

### BP-02: Ingest Phase

`ingest.ts` matches BP-02 §Ingest Phase:
- Iterates adapter refs in batches (default 20 from frozen
  `DEFAULT_INGEST_BATCH_SIZE`)
- Calls `adapter.findChanged(hint)` then `adapter.loadConversation(ref)`
  per ref
- Writes to store via `store.writeBundle(bundle)`
- Tracks which conversations changed
- Yields between batches via `await Bun.sleep(0)` (backpressure)
- Error handling: logs and skips failed adapters/conversations without
  stopping others (BP-02 §Error Handling)

### BP-02: Push Phase

`push.ts` matches BP-02 §Push Phase:
- Iterates sinks, calls `store.conversationsNeedingPush(sink.id)`
- Builds payloads with `{ attemptedRevision, conversation, messages,
  toolCalls }` — matches frozen `PushPayload` exactly
- Routes via `sinkIdsForConversation(conversation, routes)` — pure
  function import from `src/routing.ts` per BP-01 dependency rules
- Records push results per conversation via `store.recordPushResult()`
- Batches with yield between batches (backpressure)
- Error handling: on sink throw, all payloads in batch fail with error
  recorded; other sinks continue (BP-02 §Error Handling)

`mapPushErrors` (`push.ts:148-188`) defensively handles sinks that report
`failed > errors.length` by assigning generic errors to the missing count.
Good defensive code.

### BP-02: Change-Gated Push Scheduling

Push is only enqueued when ingest reports `anyChanged: true`
(`loop.ts:204,229`). Unchanged re-ingests do not trigger push. Adjacent
push items coalesce in the queue. This matches BP-02 §"Push is change-gated
and queue-coalesced."

### BP-02: Watcher Integration

`watcher.ts` wraps the existing `FileWatcher` from `src/watcher.ts` with
a `WatcherController` that supports:
- `reconcile(adapters)` — tears down and rebuilds the watcher with current
  adapter watch paths (for the periodic `reconcile-adapters` work item)
- `close()` — tears down the watcher

The `PipelineWatcherFactory` abstraction enables test injection of fake
watchers. Clean separation — tests never touch the filesystem.

Debounce uses frozen `DEFAULT_WATCH_DEBOUNCE_MS` (500ms). Watcher events
enqueue `ingest-adapter` work items with `fs-change` hints. Matches BP-02
§"Watcher Debounce (Not Pipeline Cooldown)."

### BP-02 + BP-07: Shutdown Semantics

`performShutdown()` (`loop.ts:133-175`) matches BP-02 §Shutdown and BP-07
§Shutdown Sequence:

1. Sets `stopping = true` — coordinator skips all pending normal work ✓
2. Closes watcher immediately ✓
3. Cancels periodic timer ✓
4. Discards queued normal work via `queue.discard()` ✓
5. Enqueues `shutdown-flush` (final ingest + push) ✓
6. Races coordinator against drain timeout (`SHUTDOWN_DRAIN_TIMEOUT_MS`
   from frozen `src/contracts/lifecycle.ts` = 15s) ✓
7. On clean completion: closes all sinks via `sink.close()` ✓
8. On timeout: delegates to `onShutdownTimeout` callback ✓

Timeout handling delegates exit to the caller rather than calling
`process.exit(1)` directly. This is correct — the pipeline module should
not own process exit; that belongs to the lifecycle/daemon layer (BP-07).
The `PipelineShutdownResult` reports `{ timedOut, abandonedWorkItems }`
for the caller to act on.

Shutdown scan reuses `periodic-scan` hint instead of a `shutdown-scan`
hint that doesn't exist in the frozen adapter contract. Documented with
an explicit comment (`loop.ts:29-31`). Correct decision — avoids widening
the frozen contract surface.

### BP-02: Periodic Timer

Periodic timer (`loop.ts:77-86`) enqueues `reconcile-adapters` +
`ingest-all(periodic-scan)` + `push` at `scanIntervalMs` (default
`DEFAULT_SCAN_INTERVAL_MS` = 60s from frozen config). Matches BP-02
§"Periodic timer fires" exactly.

### BP-02: Startup Work

Startup enqueues `ingest-all(startup-scan)` + `push` (`loop.ts:90-96`).
Matches BP-02 §"Initial work." Controllable via `scheduleStartupWork`
option for testing.

## Drift

### I1 — `waitForIdle()` has a micro-race on single-item dispatch (informational)

**File:** `loop.ts:114-122`
**Finding:** When exactly one work item is enqueued and the coordinator was
awaiting `queue.take()`, the item is dispatched directly to the coordinator's
waiter (bypassing the queue). At that instant, `currentWork` is still null
and `queue.isEmpty()` is true. A `waitForIdle()` call at that exact moment
would return immediately before the coordinator processes the item.

This does not affect production — the coordinator is the sole consumer and
will process the item. It affects only the test helper: a `waitForIdle()`
immediately after a single `enqueue()` may return before work completes.
Test 3 ("does not enqueue push work when ingest is unchanged") is potentially
affected — its assertion passes trivially because the coordinator hasn't
processed the ingest yet. However, the test's `finally { await shutdown() }`
block would catch any delayed push work, and the assertion is correct for
the code under test.

**Severity:** Informational. Not a production bug. Tests are correct in
outcome but slightly weak in mechanism for this case.
**Recommendation:** Could be hardened with a small coordinator-entry signal,
but not blocking.

### I2 — Non-routed conversations remain perpetually dirty (informational)

**File:** `push.ts:46-61`
**Finding:** `conversationsNeedingPush(sinkId)` returns all conversations
where `revision > last_successful_revision` for that sink. If a conversation
doesn't route to a given sink, `createPayloadForSink` returns null and the
conversation is skipped — but `recordPushResult` is never called. The
conversation remains "dirty" for that sink forever and is re-checked every
push cycle.

This is a store/routing design interaction, not a pipeline bug. The frozen
contract says "unmatched conversations push nowhere by default" — the
pipeline correctly implements this. The fix belongs upstream (e.g., store
records a "not-routed" sentinel, or `conversationsNeedingPush` filters by
routing).

**Severity:** Informational. Performance concern for stores with many
conversations and many sinks. No data correctness issue.
**Recommendation:** Track as a follow-up for the store or routing layer.

### I3 — BP-02 features not in packet scope (informational)

The following BP-02 features are absent from the implementation:
- Per-adapter call timeouts (30s/60s from `DEFAULT_FIND_CHANGED_TIMEOUT_MS`,
  `DEFAULT_LOAD_CONVERSATION_TIMEOUT_MS` in frozen contracts)
- Consecutive error tracking and automatic adapter disable after 3 failures
- RSS monitoring between ingest batches (256 MB hard limit)

All three are described in BP-02 but are NOT in the packet's acceptance
checks or deliverables list. These are reasonable scope omissions for the
initial spine — the core serialization, change-gating, and shutdown
semantics are the load-bearing structures. Timeouts and monitoring can be
added in a follow-up packet.

**Severity:** Informational (scope note, not drift).
