## Drift

### I1 — Legacy dual-interface bridge (informational)

- **File:** `src/sinks/webhook.ts`:42, 103-123
- **Finding:** `WebhookSink` implements both `LegacySink` and `SnapshotSink`.
  The `push()` method uses TypeScript overloads to accept either legacy
  `PushPayload[]` or snapshot `PushPayload[]`. Legacy payloads are rejected
  with a descriptive error (`V2_PAYLOAD_ERROR`), not silently processed.
  The constructor also accepts either `LegacySinkConfig` or
  `WebhookSinkConfig` via a union type.
- **Severity:** Informational. The bridge is explicit, legacy payloads fail
  loudly, and the approach preserves runtime compilation of the existing
  codebase. The `LegacyWebhookConfig` type union at line 18-25 picks up
  v1-only fields (`batchSize`, `developerId`, `teamId`) which are not on
  the frozen `WebhookSinkConfig`. This is a parsing-layer concern only.
- **Impact:** None. The bridge allows the webhook sink to be instantiated
  from either config shape during the v1-to-v2 transition. It should be
  removed when v1 callers are migrated.

### I2 — `formatLegacyPayloadError` return type is `string`, not `PushError`

- **File:** `src/sinks/webhook.ts`:314-331
- **Finding:** When legacy payloads are detected, the `push()` method
  returns `{ errors: string[] }` (line 117-122), matching the legacy
  `PushResult` shape, not the v2 `PushResult` shape (which has
  `errors: PushError[]`). This means the legacy rejection path returns a
  legacy-shaped result, which is correct for backwards compatibility but
  slightly surprising given the method's v2 overload signature.
- **Severity:** Informational. The legacy path is only reachable with legacy
  callers, who expect `string[]` errors. The v2 path always returns proper
  `PushError[]`. No runtime bug.
- **Impact:** None. Will disappear when the legacy interface is removed.
