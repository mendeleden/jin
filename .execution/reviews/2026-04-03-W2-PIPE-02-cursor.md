### Row 3: RSS warning/hard-limit — IMPLEMENTED

- **BP-02 §Resource Budget:** "RSS 256 MB hard, 200 MB warning. Pipeline checks
  RSS between ingest batches. Exceeding hard limit -> graceful shutdown."
- **Implementation:**
  - `loop.ts:30-31` defines `DEFAULT_RSS_WARNING_BYTES = 200 * 1024 * 1024`
    and `DEFAULT_RSS_HARD_LIMIT_BYTES = 256 * 1024 * 1024`.
  - `loop.ts:85` defaults to `process.memoryUsage().rss` via injectable
    `getRssBytes()`.
  - `enforceRssBudget()` at `loop.ts:342-366` checks RSS against both
    thresholds. Warning is logged once (de-duplicated via `rssWarningActive`
    flag). Hard limit throws `PipelineRssHardLimitError`.
  - RSS is checked: (1) before each coordinator work item (`loop.ts:201`),
    and (2) between ingest batches via `onBatchProcessed` callback
    (`loop.ts:219-222`, `loop.ts:250-253`, `loop.ts:280-283`).
  - Hard limit catch at `loop.ts:296-301` triggers `performShutdown()` which
    calls `initiateShutdown()` — a bounded graceful shutdown that closes watcher,
    cancels periodic timer, discards queued work, enqueues one `shutdown-flush`.
  - If the hard limit fires during `shutdown-flush` itself, the coordinator sets
    `shouldStop = true` and exits (`loop.ts:298-299`).

## V1 Comparison

Comparison target: `src/commands/watch.ts:236-248` (v1 RSS kill switch).

### v1 Behavior

```typescript
const RSS_WARN_MB = 200;
const RSS_MAX_MB = 256;
const checkMemory = () => {
  const rssMB = process.memoryUsage.rss() / (1024 * 1024);
  if (rssMB > RSS_MAX_MB) {
    log(`CRITICAL: RSS ${Math.round(rssMB)} MB exceeds ${RSS_MAX_MB} MB limit — exiting`);
    store.close();
    cleanup();
    process.exit(1);
  } else if (rssMB > RSS_WARN_MB) {
    log(`WARNING: RSS ${Math.round(rssMB)} MB approaching ${RSS_MAX_MB} MB limit`);
  }
};
```

- Warning threshold: 200 MB
- Hard limit: 256 MB
- Check frequency: inside periodic timer callback only (`watch.ts:253`)
- Hard limit action: `store.close()` + `cleanup()` + `process.exit(1)` (immediate)

### v2 Behavior

- Warning threshold: 200 MB — **parity** with v1
- Hard limit: 256 MB — **parity** with v1
- Check frequency: before every coordinator work item AND between ingest batches
  — **stricter than v1** (v1 only checked on periodic timer, not during ingest)
- Hard limit action: `PipelineRssHardLimitError` triggers bounded graceful
  shutdown (watcher close, timer cancel, queue discard, shutdown-flush, sink
  close) — **intentional change** from v1's `process.exit(1)`

### Verdict

| Aspect | Parity |
|--------|--------|
| Warning threshold | parity preserved (200 MB) |
| Hard limit threshold | parity preserved (256 MB) |
| Check frequency | improved — more check points than v1 |
| Hard limit mechanism | intentional BP-backed change — bounded graceful shutdown per BP-02 §Resource Budget and BP-07 §Shutdown Sequence instead of immediate `process.exit(1)` |
| Warning de-duplication | improved — v2 uses `rssWarningActive` flag to avoid log spam; v1 logs on every periodic check |

The v2 RSS guard is strictly more capable than v1. The mechanism change (graceful
shutdown vs immediate exit) is backed by both BP-02 ("Exceeding hard limit ->
graceful shutdown") and BP-07 (shutdown sequence with 15s drain budget).

## Drift

### I1 — `isSinkEnabled()` uses duck-typing to avoid widening the frozen Sink contract (informational)

- **File:** `push.ts:214-216`
- **Finding:** `(sink as Sink & { enabled?: boolean }).enabled !== false` uses
  an unsafe cast to check a property not on the frozen `Sink` interface. This
  is the correct approach under the constraint — BP-08 §419 says `pushDirty()`
  checks `sink.enabled`, and the packet says "without widening the frozen sink
  contract." The duck-type check is the minimum-viable bridge. A sink without
  an `enabled` property passes the check (enabled by default), which is correct.
- **Integration note:** The actual plumbing that copies `SinkConfig.enabled`
  onto `Sink` instances is outside this packet's boundary. The pipeline check
  is correct for the pipeline lane; the integration pass must ensure sink
  factories propagate the `enabled` flag.
- **Severity:** Informational. Correct design choice under frozen contract
  constraints. No action needed in this packet.

### I2 — RSS thresholds are local constants, not frozen contract entries (informational)

- **File:** `loop.ts:30-31`
- **Finding:** `DEFAULT_RSS_WARNING_BYTES` (200 MB) and
  `DEFAULT_RSS_HARD_LIMIT_BYTES` (256 MB) are module-local constants in
  `loop.ts`, not entries in `src/contracts/pipeline.ts`. Unlike the timeout
  constants (which W0-CODEX-01 froze), the RSS thresholds were never frozen.
  They match BP-02 §Resource Budget exactly. Configurable overrides are
  available via `RunPipelineOptions.rssWarningBytes` and
  `rssHardLimitBytes`.
- **Severity:** Informational. BP-02 values are matched. If Codex wants these
  in the frozen contract surface for cross-module consistency, that's a future
  freeze decision, not a gap in this packet.

### I3 — Consecutive error tracking remains unimplemented (informational, known gap)

- **File:** BP-02 §Per-Adapter Timeout
- **Finding:** BP-02 says "After 3 consecutive failures, the adapter is
  disabled until the next periodic scan." The worker implements per-call
  timeout enforcement but not the consecutive error counter or automatic
  adapter disabling after 3 failures. This was NOT in the packet's
  deliverables or BP Acceptance Matrix — the packet specifically asks for
  "per-call adapter timeout enforcement," not error tracking.
- **Severity:** Informational. Known remaining BP-02 gap. Same as the
  W1-PIPE-01 review's I3 item, now partially resolved (timeouts are in,
  error tracking is still deferred). Should be tracked for a future
  hardening packet.

### I4 — `onBatchProcessed` does not fire after the last batch (informational)

- **File:** `ingest.ts:122-131`
- **Finding:** The `if (start + batchSize < refs.length)` guard means the
  `onBatchProcessed` callback (and the `Bun.sleep(0)` yield) only fires
  *between* batches, not after the final batch. This means the RSS check
  via `onBatchProcessed` has a small gap for the final batch. In practice,
  the RSS check at `loop.ts:201` (before the next work item) covers this.
- **Severity:** Informational. No runtime gap — the coordinator-level RSS
  check catches it. No action needed.
